The four building blocks

Agents .claude/agents/

Autonomous specialists with their own role, tools, and model. Invoked automatically when a request matches, or explicitly: "use the pre-pr-guardian agent".

Skills .claude/skills/

Focused instruction sets forming the feature builder's internal pipeline — UI conversion, API wiring, structure validation, self-review.

Commands .claude/commands/

Slash commands typed in a session, e.g. /commit-message. Deterministic, single-purpose, instant.

Templates & Tools template/ · tools/

The developer fills the feature template; the prompt generator turns it into a build prompt — it never writes code itself.

02Workflows — How It Chains Together

The toolkit is designed as pipelines, not isolated tools. Pick the lane that matches the size of the work.

Lane A — New feature (from Figma + API)
feature-template
Developer fills in name, Figma link, API spec, behavior
→
feature-prompt-generator
Turns raw inputs into a structured build prompt (never codes)
→
flutter-feature-builder
Builds the feature end-to-end using its 4 skills
→
reviewers
clean-code · performance · architecture
Inside the builder: figma-to-flutter → api-integration → project-architecture → flutter-reviewer.
Lane B — Small / vague task ("fix avatar in weekly sheet")
flutter-task-refiner
Investigates the codebase, produces an implementation-ready spec
→
flutter-feature-builder
Executes the refined spec
→
flutter-clean-code-reviewer
Quality check on the diff
The refiner is read-only — it hands over a spec with target files, requirements, edge cases, and acceptance criteria.
Lane C — Bug fix / refactor
flutter-bug-fixer
Root-cause first, minimal fix, verify with analyze + test
or
refactoring-architect
Behavior-preserving cleanup, mandatory verification
→
pre-pr-guardian
Pre-flight check before opening the PR
Lane D — Before & at the PR (every branch)
pre-pr-guardian
Catches bugs before the PR exists · verdict: READY / NOT READY
→
/commit-message
Conventional Commit line from staged diff
→
senior-pr-reviewer
Formal production-grade review · APPROVE / REQUEST CHANGES
→
architecture-auditor
Optional: 3-year maintainability audit for structural changes
Rule of thumb: builders and fixers edit files; every reviewer is read-only and ends with an explicit verdict. Run at least pre-pr-guardian on every branch before opening a PR — it is the cheapest place to catch a production bug.

04Builder Agents

These agents create or shape production code. All of them enforce Clean Architecture and the project design system.

flutter-feature-builder OpusEdits files
Tools: Read · Write · Edit · Grep · Glob · Bash

Senior Flutter engineer that builds production-ready features end-to-end from Figma designs, API docs, or requirements — scaffolding data/domain/presentation, wiring Cubit/Bloc + GetIt + Dio + GoRouter, with AR/EN localization and responsive design.

Execution pipeline
  • Analyze inputs → figma-to-flutter → api-integration → validate with project-architecture → generate code → apply UI composition rules → self-check with flutter-reviewer.
Hard UI composition rules
  • Never a full screen in one file — split into logical widgets (LoginHeader, LoginForm…), one top-level widget class per file.
  • No _buildX() methods returning widgets — extract a real widget class instead, even for single-use blocks (see §09).
  • UI repeated 2+ times becomes a widget; forms, lists, animations, and large layouts are always extracted. Screens only compose, navigate, and connect state.
flutter-figma-implementation-expert Inherits modelEdits files
Tools: Read · Write · Edit · Grep · Glob · Bash · Figma MCP (design context, screenshots, metadata, variables, assets)

Pixel-perfect UI from a specific Figma node: exact spacing, typography, colors, radii, and layout hierarchy. Plans first (colors / typography / spacing / components), implements, then compares against Figma before finishing.

Mandatory project conventions
  • flutter_screenutil everywhere (.w .h .r .sp) — designSize 402×874 = the Figma artboard, so Figma px map 1:1. Never raw pixel doubles.
  • Colors only via AppColors (add a token if missing — never inline Color(0xFF…)); typography via TextStyles + .copyWith(fontSize: X.sp); spacing via AppSpacing; assets in AppAssets/AppIcons; strings via context.tr with AR + EN entries.
  • Finishes only after flutter analyze is clean on changed files (zero warnings).
flutter-task-refiner SonnetRead-only
Tools: Read · Grep · Glob · Bash

Turns short, vague requests ("image not loading in profile", "use same loader as leaderboard") into implementation-ready specs for the feature builder. Actively investigates the codebase — never trusts user-provided file names.

Output spec structure
  • ⚠️ Needs Confirmation (blocking gaps) → Title → Context → Goal → Target Files (real path:line) → Requirements incl. edge cases (null/empty/loading/error) → Constraints → Acceptance Criteria → Confidence + labeled assumptions. Never silent guessing of business logic.
Lane
  • Bug fixes, UI tweaks, refactors, small-to-medium changes, migrations. Not full features from Figma/API — that's the feature-prompt-generator's job.

05Fixer Agents

Both edit files — and both are bound by strict safety rules: minimal change, verified results, no silent behavior changes.

flutter-bug-fixer Inherits modelEdits files
Tools: Read · Edit · Bash · Grep · Glob

Senior debugging engineer for runtime errors, build failures, state management problems, performance issues, and architecture violations. Root cause comes before any fix.

Six-step process
  • Read issue + related files → determine root cause and explain why → propose options, choose the safest → implement (update tests if needed) → verify with flutter analyze, dart format ., flutter test → report root cause, files changed, risks, and verification steps.
  • Checks the full Flutter problem space: rebuilds, memory leaks, async races, Bloc/Cubit and Riverpod issues, navigation, DI, null safety, BuildContext misuse, platform-specific issues.
Never
  • Random fixes · ignored analyzer warnings · architecture changes without justification · new packages unless necessary.
refactoring-architect Inherits modelEdits files
Tools: Read · Write · Edit · Bash · Grep · Glob

Staff-level, behavior-preserving refactoring: architecture, readability, maintainability, performance, consistency — while the app behaves exactly as before. Knows this repo's Riverpod/Freezed/GoRouter conventions in depth.

Non-negotiable rules
  • Behavior is frozen. If a change would alter business rules, API contracts, navigation, or UI behavior, it stops and reports it under "Behavior Changes Required" instead.
  • Never edits generated files (*.g.dart, *.freezed.dart…) — regenerates with build_runner after touching annotated classes.
  • Stays in scope, never commits or pushes, and prefers many small safe changes over big rewrites.
  • Mandatory verification — must actually run and report: dart format, flutter analyze (clean), flutter test (60% threshold). Never deletes a test to go green; "compiled mentally" doesn't count.
Targets
  • Guard clauses over nested ifs · meaningful names (no res/tmp/doWork()) · methods ~20–40 lines · dead code removal (git has history) · explicit null handling over ! · no empty catch blocks · const constructors and immutability.
  • Reports: Summary · Changes · Verification · Behavior Preserved · Behavior Changes Required · Risks · Suggested Follow-ups.
When to pick which: something is broken → bug-fixer. Something is ugly but working → refactoring-architect. If you only want the findings without edits, use the read-only flutter-clean-code-reviewer instead.

06Reviewer Agents

Five read-only specialists, each with a distinct lens and an explicit verdict. By default they review the current branch diff, not the whole codebase.

flutter-clean-code-reviewer OpusRead-only
Lens: Clean Code · SOLID · Clean Architecture · project conventions  |  Tools: Read · Grep · Glob · Bash

Staff-engineer-strict review of naming, separation of concerns, widget decomposition, duplication, and consistency — plus the repo's hard rules: no hardcoded strings, no magic values, one widget class per file, log() never print().

Output
  • Issues (Critical/Major/Minor · file:line · problem · fix) → refactored examples → summary with top priorities. Defers performance findings to the performance reviewer.
flutter-performance-reviewer OpusRead-only
Lens: Rendering · rebuilds · memory · 60fps+  |  Tools: Read · Grep · Glob · Bash

Hunts unnecessary rebuilds, missing const constructors, heavy build methods, unpaginated lists, over-emitting Cubits, deep widget trees, uncached images, repeated API calls, and missing debouncing.

Output
  • Issues → severity (High/Medium/Low) → concrete fixes → optimized structure when needed. Small performance issues are not ignored.
flutter-architecture-auditor OpusRead-only
Lens: 3-year maintainability  |  Tools: Read · Grep · Glob · Bash

Principal-architect audit of layer boundaries and dependency direction: Domain must not depend on Data or frameworks, DTOs must not leak into Domain, UI holds no business logic. Also weighs scalability, reusability, premature abstraction, and god classes/widgets.

Verdict
  • PASSPASS WITH CONCERNSFAIL + scalability grade (Excellent → Poor) + architectural debt introduced. Evidence-based, no personal preferences.
pre-pr-guardian OpusRead-only
Lens: Bug prevention before the PR exists  |  Tools: Read · Grep · Glob · Bash

Principal-engineer pre-flight of the branch: logic bugs, null safety, async/race conditions, error-handling gaps, lifecycle/memory/stream leaks, localization and accessibility problems, missing tests.

Verdict
  • Change Summary → Blocking Issues → Improvements → Suggestions → Test Cases To Verify → READY / NOT READY. Only actionable findings — no praise, no invented issues.
senior-pr-reviewer OpusRead-only
Lens: Formal production-grade PR review  |  Tools: Read · Grep · Glob · Bash

Reviews the full diff and every commit as if it ships tomorrow: correctness, Flutter lifecycle/state, architecture, API & data handling, security (secrets in logs, authorization, unsafe input), and test coverage.

Verdict
  • PR Summary → findings with impact + recommendation → production risk & confidence → APPROVEAPPROVE WITH SUGGESTIONSREQUEST CHANGES.

07Skills — The Feature Builder's Pipeline

Four focused skills run in sequence inside flutter-feature-builder. Together they take a feature from design to reviewed code without leaving the project's architecture.

1 · figma-to-flutter

Converts Figma designs into Flutter UI: analyzes layout, typography, spacing, colors, and components, and detects reusable widgets.

  • Uses: AppColors · AppSpacing · TextStyles · ScreenUtil
  • Avoids: hardcoded dimensions, duplicated widgets, inline styling
  • Generates: screens, widgets, layouts — UI only, never repositories/use-cases/API logic
2 · api-integration

Generates the networking and business-logic stack to project standards.

  • Produces the full chain: Entity → Model → Mapper → Remote DataSource → Repository → UseCase → Cubit → States → DI registration
  • Uses: DioConsumer · BaseRepositoryMixin · existing error handling
  • Maps: network, server, unauthorized, and parsing errors — raw exceptions never reach the UI
3 · project-architecture

Validates that every generated feature matches the existing project structure — layers are never bypassed.

  • Structure: data/ (datasources · models · mappers · repositories), domain/ (entities · repositories · usecases), presentation/ (cubit · pages · widgets)
  • Core stack: DioConsumer · BaseRepositoryMixin · Failure/Exception hierarchies · GetIt · GoRouter · Cubit/BLoC
4 · flutter-reviewer

Self-review gate before the builder returns its output.

  • Checks: layer separation, no business logic in UI, no direct API calls from widgets, meaningful names, small focused classes, no unnecessary rebuilds, proper state management / DI / navigation / localization
  • Delivers: issues found, suggested improvements, final approval
Why skills instead of one giant prompt? Each stage has a crisp contract — the UI skill can't invent API logic and the API skill can't restructure the architecture. That keeps generated features uniform across the whole team regardless of who prompts.

08Command · Template · Tool

⌘ /commit-message — Conventional Commits from the staged diff

Analyzes git diff --staged and returns exactly one line — no markdown, no explanation. Present tense, short, meaningful, optional scope.

Types
feat      new feature
fix       bug fix
refactor  code restructure
chore     maintenance
ui        UI changes
api       API integration
test      adding/updating tests
docs      documentation
Examples
feat(auth): add login validation
fix(api): handle timeout error in user request
refactor(core): simplify repository structure
ui(login): improve form layout responsiveness

📋 feature-template — what a developer fills in

The standard request form for a new feature. Complete it, then hand it to the feature-prompt-generator.

## FEATURE NAME      Login Feature
## FIGMA             https://www.figma.com/file/xxxxx  (or MCP link)
## API SPEC          POST /auth/login  + request/response JSON
## BEHAVIOR          user actions · loading · success flow · error handling
## REQUIREMENTS      AR/EN · responsive · Clean Architecture · existing theme · Cubit
## NOTES (optional)  exclusions, e.g. "social login not included"

⚙️ feature-prompt-generator — template in, build-prompt out

Converts the filled template into a structured, production-ready prompt for flutter-feature-builder: context, behavior (incl. loading/success/error/edge cases/navigation), requirements, UI guidelines, architecture guidelines, and acceptance criteria.

Hard execution boundary: this tool only generates prompts. It never implements, edits files, or emits Dart code — even if the input says "work on it", "fix it", "implement", or "build". Those words are deliberately ignored; the output is always a prompt artifact for the downstream builder.
  • Baked-in requirements: Clean Architecture, Cubit/BLoC, responsive UI, AR/EN localization, theme system, component reuse.
  • Baked-in UI rules: small reusable widgets, no monolithic screens, ~120–150 lines max per widget file, strict design-system adherence.

09House Rules Cheat Sheet

The project's non-negotiables — builders apply them, reviewers flag every violation.

Strings & localization

  • No hardcoded user-facing text — use AppLocalizations / context.tr
  • Constant string keys live in AppStrings
  • Every string ships with both AR and EN entries; all UI must work RTL

Design tokens — no magic values

  • Colors: AppColors only — never inline Color(0xFF…); add a token if missing
  • Spacing / radii / durations: AppSpacing, theme tokens, or named constants
  • Typography: TextStyles + .copyWith(fontSize: X.sp) — ClashGrotesk & Sentient
  • Assets registered in AppAssets / AppIcons

Responsive sizing

  • flutter_screenutil: .w width · .h height · .r radius · .sp font
  • designSize 402×874 = the Figma artboard → Figma px map 1:1
  • Use flex in Rows/Columns; never raw pixel doubles

Widget composition

  • One top-level widget class per file — always
  • Small composable widgets over monoliths (~120–150 lines/widget file)
  • Screens compose; they never implement UI blocks inline
  • UI repeated 2+ times → extract a widget

Architecture

  • Clean Architecture per feature: data / domain / presentation
  • No business logic in widgets; no direct API calls from UI
  • Domain depends on nothing; DTOs never leak into Domain
  • Never bypass DioConsumer / BaseRepositoryMixin / Failure hierarchy

Hygiene & verification

  • log() — never print()
  • Never edit generated files (*.g.dart, *.freezed.dart) — re-run build_runner
  • Before done: dart format · flutter analyze clean · flutter test (60% coverage)
  • No commented-out code — git has the history

The one rule everyone gets wrong

Helper methods that return widgets are banned — they lose their const constructor and rebuild boundary, so they rebuild with the entire parent. Applies even for single-use blocks:

❌ NEVER 
Widget _buildActionButtons({double? size}) {
  return Row(children: [...]);
}
✅ ALWAYS 
// profile_header_actions.dart
class ProfileHeaderActions extends StatelessWidget {
  const ProfileHeaderActions({super.key,
    required this.onSettings, ...});
  ...
}
